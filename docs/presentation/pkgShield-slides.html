pkgShield · Background and problem02 / 12

Not every package is a good guest.

156%

rise in malicious packages in one year (Sonatype, 2024)

Fake names
Look-alike names such as “reqeusts” trick developers into installing the wrong package.
Stolen accounts
An attacker takes over a maintainer account and adds harmful code to a trusted package.
Known flaws
Some packages carry known vulnerabilities with a CVSS score.
Who is hit
Developers and teams that build software from open-source packages.
pkgShield · Motivation03 / 12

Who let this package in, and why?

The gap
Detectors flag strange behaviour. They give no single risk score and no lasting record of who approved or blocked a package.
The idea
A package request is a database event. Put the check where the data and the rules already live.
Why Oracle
Triggers stop the request. Autonomous transactions keep the evidence. A scheduler keeps watching.
pkgShield · Objectives04 / 12

One goal, five steps.

Main objective

Build an Oracle PL/SQL database that checks every requested package and blocks risky ones before they reach a build.

01
Load real advisory and malicious-package data into 3NF tables.
02
Give each package version a risk score from 0 to 100.
03
Block blacklisted or high-risk requests with a trigger.
04
Keep every block in an audit log that survives a rollback.
05
Re-score pending packages on a schedule and raise alerts.

pkgShield · Proposed solution and innovation07 / 12

A security guard at the door.

1 RequestA build project sends a package list (deployment manifest).
→
2 ScorePL/SQL gives the package version a risk score, 0 to 100.
→
3 DecideA trigger blocks blacklisted or high-risk packages.
→
4 RecordThe block is written to an audit log that survives the rollback.

Innovation · Smart automation

A DBMS_SCHEDULER job re-scores pending packages when new advisories arrive and adds warnings to SECURITY_ALERTS. Shown live on the Oracle database.

pkgShield · Planned database08 / 12

Nine tables, 3NF.

Primary keys, foreign keys, sequences and check constraints. The audit log has no foreign keys, so its records stay even if other rows are deleted. Exact keys are fixed in Phase II.

pkgShield · PL/SQL approach09 / 12

Each feature, and where it is used.

FeatureWhere it is used
Autonomous transactionWrites the audit record and quarantine flag, so a blocked request is still on record after the insert rolls back.
Risk-score functionCalled for each manifest. Uses the highest CVSS score, maintainer reputation and account age, and the name check.
Name-check functionUTL_MATCH.EDIT_DISTANCE compares a requested name to popular ones. “reqeusts” is 2 edits from “requests”.
Cursor with FOR UPDATELocks a pending manifest row while it is checked, so two sessions cannot decide the same request.
TriggerOn DEPLOYMENT_MANIFESTS. A blacklisted or high-risk package raises RAISE_APPLICATION_ERROR and the request stops.
Packages and exceptionsGroup the code. Named exceptions handle a missing package or bad data without crashing.
DBMS_SCHEDULER jobRe-scores pending packages on a schedule and inserts rows into SECURITY_ALERTS.

pkgShield · Future improvements and limitations11 / 12

What it does not do yet.

Limitations

  • Maintainer data and download trends are made up by a script.
  • Risk weights are set by hand, not learned from data.
  • The name check uses edit distance only.
  • No live link to a real package registry.

Future improvements

  • Load new OSV advisories automatically.
  • Add a dashboard on the alerts table.
  • Send e-mail alerts to the team owner.
  • Check affected version ranges, not only package names.
